### 2.2.1 RANDOM FOREST
**[SUPERVISED] [TABULAR] [CLASSIFICATION / REGRESSION] [BAGGING]**

**LEVEL 1: TRIAGE**
* **Input / Output:** Input: Numerical or categorical data (scaling not strictly necessary). Output: Predicted class (majority vote) or expected value (mean).
* **GO (Use when):** Absolute starting baseline for tabular data. When you want a robust model "out-of-the-box" with zero time available for hyper-tuning.
* **NO-GO (Avoid when):** Inference latency is critical at the millisecond level (final model is very heavy). Need to extrapolate trends outside the historical training data.

![Random Forest Classifier](../pictures/randomforest.png)

**LEVEL 2: OPERATIONS**
* **Principles of operation:**
  * **Bagging (Bootstrap Aggregating):** Creates hundreds of independent Decision Trees. Each is trained on a random sample with replacement from the original dataset.
  * **Random Subspace:** At each node split, the tree considers only a random subset of features (decorrelating the trees).
  * **Final Vote:** In classification the forest votes by majority; in regression it returns the mathematical mean of all trees.

| PROS | CONS |
| :--- | :--- |
| Almost immune to Overfitting compared to a single tree. | Black-box: it loses the traceability and visual interpretability of the Decision Tree. |
| Highly parallelizable in training (uses multi-core well). | Model can be very heavy in RAM if trees and depth are not limited. |
| Invariant to feature scale and robust to outliers. | Slow in inference if the number of trees (`n_estimators`) is huge. |

**LEVEL 3: DEEP DIVE & TROUBLESHOOTING**
* **Key Hyperparameters:**
  * `n_estimators`: Number of trees. Increasing it improves performance and stability, but linearly saturates time and memory. (Above 300-500 rarely gives tangible benefits).
  * `max_features`: Subset of features to evaluate at each split. **Low** = Very decorrelated trees (reduces variance). Standard: square root of the number of features.
  * `max_depth` / `min_samples_leaf`: Similar to CART, but here one can allow deeper and more complex trees thanks to Bagging.
* **Typical Loss Function:** Gini Impurity (Classification), [MSE](0%20-%20hot%20to%20use.md#essential-acronym-glossary) (Regression) calculated at the level of each base tree.
* **Common Pitfalls & Quick Fixes:**
  * **Pitfall:** Gigantic pickled file (GBs) and failed deployment due to Out Of Memory ([OOM](0%20-%20hot%20to%20use.md#essential-acronym-glossary)) on the production server.
    * *Quick Fix:* Limit the `max_depth` hyperparameter (e.g. to 10-15) or reduce `n_estimators` drastically. Performance will drop marginally, but the file size will collapse vertically.

### 2.2.2 GRADIENT BOOSTING MACHINES (XGBoost, LightGBM, CatBoost)
**[SUPERVISED] [TABULAR] [CLASSIFICATION / REGRESSION] [BOOSTING] [SOTA](0%20-%20hot%20to%20use.md#essential-acronym-glossary)**

**LEVEL 1: TRIAGE**
* **Input / Output:** Input: Numerical and categorical data (LightGBM and CatBoost handle them natively). Output: Predicted class or continuous value.
* **GO (Use when):** You are looking for the maximum absolute performance ([SOTA](0%20-%20hot%20to%20use.md#essential-acronym-glossary)) on tabular data. Kaggle challenges. When you have enough time for hyper-tuning.
* **NO-GO (Avoid when):** Very noisy data with uncertain targets. Projects requiring absolute and immediate explainability (unless using SHAP in post-processing).

**LEVEL 2: OPERATIONS**
* **Principles of operation:**
  * **Sequential Training:** Unlike Random Forest, here the trees are not independent. Each new tree is trained to correct the errors (residuals / gradients) of the previous tree.
  * **Learning Rate (Shrinkage):** The impact of each new tree is scaled by a factor (learning rate) to avoid overly abrupt jumps and encourage gradual learning.
  * **The Three Families:**
    * *XGBoost:* The industrial standard, robust but greedier with resources.
    * *LightGBM (Microsoft):* Leaf-wise growth, continuously bins data (histograms). Extremely faster and lighter.
    * *CatBoost (Yandex):* Mathematically optimized for datasets with hundreds of high-cardinality categorical variables.

| PROS | CONS |
| :--- | :--- |
| Predictive performance superior to any [ML](0%20-%20hot%20to%20use.md#essential-acronym-glossary) model on tabular data. | High Overfitting risk if not monitored adequately (Early Stopping is mandatory). |
| Excellent feature importance (Gains, Cover). | Sequential training: harder to parallelize than Bagging. |
| Native handling of missing values (and categorical features for LGBM/CatBoost). | Requires careful and meticulous tuning of hyperparameters (sensitive to configuration). |

**LEVEL 3: DEEP DIVE & TROUBLESHOOTING**
* **Key Hyperparameters (Fundamental trade-off):**
  * `learning_rate` (eta) & `n_estimators`: They are inversely proportional. **High Learning Rate (e.g. 0.1)** = Requires few trees, fast training, risk of missing the local minimum. **Low Learning Rate (e.g. 0.01)** = Requires thousands of trees, better generalization, longer training.
  * `max_depth` (XGBoost) or `num_leaves` (LightGBM): Control the complexity of the base tree. Keep them low (e.g. max_depth between 3 and 8).
  * `subsample` / `colsample_bytree`: Introduce stochasticity (similar to Random Forest) to fight overfitting.
* **Typical Loss Function:** Any differentiable function (Log-Loss, RMSE, [MAE](0%20-%20hot%20to%20use.md#essential-acronym-glossary), Poisson, custom objective).
* **Common Pitfalls & Quick Fixes:**
  * **Pitfall:** Training loss collapses to zero, but validation loss explodes after the first iterations (extreme Overfitting).
    * *Quick Fix:* 1) Strictly enable `early_stopping_rounds`. 2) Lower `learning_rate`. 3) Lower `max_depth`. 4) Increase regularization `reg_alpha` (L1) or `reg_lambda` (L2).
  * **Pitfall (LightGBM specific):** Model is excessively fitted on small datasets.
    * *Quick Fix:* LightGBM grows leaf-wise and is very aggressive. On small datasets, artificially force `max_depth` to low values (e.g. 3-4) and limit `num_leaves` (< 2^(max_depth)).
